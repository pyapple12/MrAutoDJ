# 按 x.progress.md 章节执行任务（progress-task）

用户指定 x.progress.md 中的一个任务章节（标题/编号由用户输入），按固定流程执行。

## 触发场景

用户消息形如：

- "研究 x.progress.md 中 ### PL001.2 曲库扫描"
- "按 x.progress.md 中 X 章节执行"
- "推进任务 ### PL001"
- "推进任务 FIX004"

章节编号（如 PL001.2、FIX004.3、PATCH002.1）是用户对任务的标识，对应 x.progress.md 中的具体条目。编号可以是任务组（如 PL001、FIX004）或单个子任务：指定任务组时覆盖该组全部子任务，指定子任务时只执行该条。（历史字母系列 D/E/F/G/H/I/J 章节同样适用本流程——按既有条目中的"做法/验证"执行。）

## 执行流程（MR 2026-11-05）

> 工具无关约定：本 skill 只描述**能力**，不绑定具体 harness 的工具名——环境有同名工具（如 `edit`、todo 清单）就直接用，没有就用等价通用手段（清单写进回复、用可用的文件编辑工具做精确替换），**不得因工具名不同而跳过步骤**。

### Step 1：研究

- 通读用户指定的 x.progress.md 章节，确认：任务范围、已有做法说明（`—— 做法；验证：` 格式：`——` 后为执行要点，`验证` 为检验方式）、已有验证方式说明
- 必要时读相关代码上下文（只读）

### Step 2：形成自己的 todo list

- 建立并维护一份细分任务清单：标注优先级（high/medium）、覆盖该章节所有子任务
- **工具无关**：环境有 todo/清单类工具就用工具；没有就在回复里以编号清单列出并逐条跟踪状态——两者等价，**不得因无工具而跳过本步**
- 执行中持续更新：完成即勾、拆分即补；收尾时清单状态与 x.progress 勾选一致

### Step 3：形成检验方案

- 每个任务明确"完成后的检验标准"：可执行、可断言
- 采用 TDD 风格：先写探针（`.temp/probe_{主题}.py`，沿用既有 probe 的 assert_true/FAILURES 汇总模式），修复前跑应 FAIL（复现问题/证明探针有效），修复后跑 PASS
- 包含回归验证（既有探针重跑）+ 冒烟（AGENTS.md「运行与验证」的 import 清单）
- 涉及视觉的出无头截图（`QT_QPA_PLATFORM=offscreen` + `grab()` → `.temp/ui_preview/`）

### Step 4：执行任务

- 逐项实现，遵守 AGENTS.md 规范（工程原则 KISS/DRY、错误策略"不崩溃不阻塞有提示能自愈" + 容错登记制、`#` 注释体系与文件尾说明区、类型注解、pathlib 强制、参数走 config/static/*.json、音频数组 `(N,2) float32` 约定、import 三段顺序、回调内零 IO/零分配）
- **层级红线**：`utils/` 无业务依赖；原语控件（`ui/widgets/`）零业务依赖（禁 import modules/）；`modules/` 无 GUI 依赖——新增代码不得破坏单向分层
- **用户数据红线**：`config/user_config.json`、`cache/` 为运行时数据不入仓库；分析缓存数据库只读连接
- **修改既有文件用 edit 类工具精确替换**（禁止 Bash 内 sed/python -c 改文件，Mimosa 钩子会拦截）；临时脚本/文件一律写入 `.temp/`
- 每项修复后立即跑对应检验

### Step 5：用检验方案验证

- 跑探针确认 PASS；跑全量回归（`.temp/` 既有 probe 逐个）+ 冒烟 import
- **修复验收（每批修复后强制，防"修复引入新缺陷"）**：每批修复完成后、全量回归前，逐项对照原问题做**反向验证**（原问题是"hop 引用已删变量"→验收"CLI 带 cues 分析不崩"；原问题是"位置域漂移"→验收"烘焙后 CUE 重映射正确"），验收结果记录在 .temp/ 下
- **验证样例独立化**：探针结构性样例必须来自真实数据快照或独立证据，禁止手写与实现同源的 mock 自证；手写 mock 仅用于行为验证（如 mock 无音频设备）
- **多模态节点**：任务涉及读图（截图核对、布局对照）且当前模型无视觉能力时，停下通知用户切换多模态模型；未实际读到图严禁声称"能读到"或编造图片内容
- 确认正确后才勾选完成

### Step 6：确认完成与汇报

- 勾选 x.progress.md 对应条目（附日期与验证结果；**TDD 类条目须带红灯 → 绿灯证据**：先跑失败用例的输出摘要 + 修复后通过数），勾选注记格式 `（YYYY-MM-DD 已验证：{一句话结论}）`
- 汇报：检验方案结果表 + 修改文件清单

## 硬性约束

- 检验方案**先于**实现（TDD：先 FAIL 后 PASS）
- "完成任务后，需要使用检验方案验证，确认正确后才能认为完成"——未验证不算完成
- 不擅自执行 git 写操作；**用户明确要求提交/推送时按其指示执行**（提交前仍须 `git status` + `git diff`（含 `--stat`）核对改动范围并交用户确认；commit 标题按 AGENTS.md 四段式版本规范）
- 不擅自做章节范围外的操作（如改版本号、改配置），只做任务内的事
